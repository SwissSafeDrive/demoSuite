## 1. Repo structure and how to run

- `app/` is the npm frontend. `app/src/` holds the shell, three views in `pages/`, API client, and stylesheet. `app/src-tauri/` is the Rust desktop wrapper, configuration and bundled resources. `backend/` is the local Python API, SQLite models and schemas, and runner that seeds the demo. The root holds the project rules and README, with handoff and decision records under `docs/` and release tooling in `scripts/`. (`app/package.json:1–23`, `app/src/main.jsx:1–10`, `app/src/App.jsx:1–8`, `app/src-tauri/tauri.conf.json:6–11`, `app/src-tauri/tauri.conf.json:24–37`, `backend/backend_runner.py:8–19`, `README.md:26–31`, `scripts/build_release.sh:4–8`)
- **Frontend development.** From `app/`, run `npm ci` and `npm run dev` for Vite on port 1420. `npm run build` produces the frontend build and `npm run preview` serves that build. Vite alone can render the shell, but the registry calls require the Tauri-provided API session. In a plain browser the client falls back to loopback with an empty token, so the protected endpoints reject those requests. (`app/package.json:6–10`, `app/vite.config.js:15–18`, `app/src/api/client.js:5–55`, `backend/main.py:86–95`)
- **Desktop development and release.** After npm dependencies are installed, `npm run tauri dev` starts Vite through the Tauri config and needs the expected backend resource available to Tauri. From the root, `bash scripts/build_release.sh` builds the Apple Silicon backend with PyInstaller, bundles the frontend and backend into the macOS app, then signs and packages the app and DMG. The script replaces existing outputs at its configured destination. The packaged app starts its own backend, so a packaged demo can run with loopback access and no external service. (`app/package.json:6–10`, `app/src-tauri/tauri.conf.json:6–11`, `app/src-tauri/tauri.conf.json:34–36`, `app/src-tauri/src/lib.rs:107–149`, `scripts/build_release.sh:8–39`, `scripts/build_release.sh:51–78`, `backend/backend_runner.py:122–130`)
- **Backend only.** Install `backend/requirements.txt` in a Python environment and run `python backend/backend_runner.py` from the repo root for local API work. The runner seeds demo data and serves Uvicorn on loopback port 8765 by default. For direct API calls, supply a local `SSD_SESSION_TOKEN` to the runner and send the matching `X-SSD-Session` header. Use a separate `SSD_DATA_DIR` if keeping test data outside the checkout. (`backend/backend_runner.py:107–130`, `backend/database.py:6–17`, `backend/main.py:31–42`, `backend/main.py:86–95`)

## 3. Recorded media and overlays

- 0.2.2 has no recorded-video playback flow, tracked clip assets, video endpoint, or configured video formats. The only `video` element receives a live `MediaStream` through `srcObject` and has no playback controls. The review screen renders an `img` or a demo placeholder. The component revokes the URL on cleanup and falls back to the placeholder if the image cannot be fetched. Upload accepts JPEG, PNG and WebP by declared type and file signature, while the serving endpoint always labels the response `image/jpeg`. The built-in camera uploads JPEG. ## 4. Live camera

- Opening **Camera in diretta** requests the local camera on mount at 1280×720 constraints with audio disabled. It attaches the stream to a muted, inline video. Stop and unmount clear the capture timer and stop the media tracks. macOS declares application camera usage. If access fails or the browser API is unavailable, the view shows a no-camera demo state with retry and return-to-registry actions. That fallback has no substitute video stream. (`app/src/pages/CamaraEnVivo.jsx:19–68`, `app/src/pages/CamaraEnVivo.jsx:118–178`, `app/src/pages/CamaraEnVivo.jsx:209–241`, `app/src-tauri/Info.plist:4–6`)
- Manual or timed capture copies the current frame to a hidden canvas, encodes JPEG at quality 0.85 and uploads it with location `Camera locale` and fixed confidence 0.75. FastAPI saves the image and creates a pending `camara` record. This is real capture with a demo score and generated identifier. Every capture creates a row without a detector or tracker. Captures are temporary, with a file cap of ten and cleanup on shutdown. The runner removes stale camera rows on the next launch. (`app/src/pages/CamaraEnVivo.jsx:70–109`, `app/src/pages/CamaraEnVivo.jsx:244–246`, `app/src/api/client.js:77–102`, `backend/main.py:35–62`, `backend/main.py:112–127`, `backend/main.py:268–295`, `backend/backend_runner.py:15–24`)
- Leave camera permission, streaming and capture upload outside the 30 Nov playback path. The live view's media container is a layout reference. Its `objectFit: "cover"` crops the image when aspect ratios differ, so the recorded player needs its own coordinate mapping. (`app/src/pages/CamaraEnVivo.jsx:196–219`)

## 5. Registry and click-through

- The registry contract is Python `Registro` with Pydantic `RegistroBase` / `RegistroOut`. Rows carry numeric `id`, event `inf_id`, timestamp, confidence, location, technical demo identifier, state, origin and informational note, with optional image path, agent ID and decision time. Origins in the current data are `simulato` and `camara`. (`backend/models.py:6–25`, `backend/schemas.py:6–24`, `backend/backend_runner.py:71–87`, `backend/main.py:282–291`)
- **Registri** mounts `Dashboard`, which loads `GET /api/registros` and `GET /api/estadisticas` concurrently. The API returns newest records first and aggregates counts and average confidence across the database. The dashboard shows total, pending, reviewed and average confidence. The reviewed card counts only rows in the exact `revisado` state. Its state, minimum confidence and location/event ID search filters run in React. There is a refresh action and a reset-filters action. (`app/src/App.jsx:29–35`, `app/src/App.jsx:46–49`, `app/src/pages/Dashboard.jsx:14–47`, `app/src/pages/Dashboard.jsx:112–183`, `app/src/api/client.js:58–64`, `backend/main.py:143–149`, `backend/main.py:193–233`)
- The current list is a card grid with placeholder thumbnails, location, timestamp, state and confidence. Clicking a card passes the whole row to `App`, which stores it and switches to `RegistroDetalle`. Returning remounts the dashboard and reloads its records with default filters. The existing `GET /api/registros/{id}` and `getRegistro(id)` support direct lookup, though the current click-through uses the list payload. (`app/src/pages/Dashboard.jsx:4–33`, `app/src/pages/Dashboard.jsx:185–215`, `app/src/App.jsx:6–18`, `app/src/App.jsx:46–56`, `app/src/api/client.js:66–68`, `backend/main.py:152–161`)

## 6. Review console and data provenance

- **Dettaglio registro** shows the captured still or placeholder, event ID, time, location, origin, confidence, demo identifier, current state and optional agent and decision timestamp. It also shows the record's informational note. There is no plate blurring in this flow. The camera canvas copies the full frame, the API saves its bytes, and the detail view displays the resulting image directly. The technical demo identifier is generated seed/capture metadata. (`app/src/pages/RegistroDetalle.jsx:82–151`, `app/src/pages/RegistroDetalle.jsx:198–200`, `app/src/pages/CamaraEnVivo.jsx:70–77`, `backend/main.py:268–295`, `backend/backend_runner.py:40–80`)
- The reviewer can **Scarta**, **Marca per revisione** or **Conferma infrazione**. Each sends `PATCH /api/registros/{id}/decision` with a state and default demo agent ID. The backend validates the state and persists state, agent ID and UTC decision time in SQLite, overwriting the previous decision fields on that row. The screen updates state and shows feedback, while agent and decision time still come from the original row until it is reloaded. The screen explicitly leaves the final decision with the human operator. (`app/src/pages/RegistroDetalle.jsx:60–73`, `app/src/pages/RegistroDetalle.jsx:133–195`, `app/src/api/client.js:70–75`, `backend/main.py:164–190`)
- The packaged runner populates an empty database with four simulated pending rows with invented locations/confidences and no images. The separate `seed.py` script also supplies four simulated rows when run against an empty database. The list still runs against a real local API, and review writes persist. Live camera frames are real when available, but the score and technical ID are demo values. There are no seeded recorded clips, track IDs, boxes or Passes. (`backend/backend_runner.py:15–36`, `backend/backend_runner.py:38–90`, `backend/seed.py:6–35`, `backend/main.py:143–149`, `backend/main.py:164–190`, `backend/main.py:268–295`, `backend/models.py:6–25`, `app/src/pages/CamaraEnVivo.jsx:79–93`)
